## 一、总体评估

| 维度 | 结论 |
|---|---|
| 项目自有代码规模 | 约 45,000 行（src/ ~38k + HandTracker 自有 ~3k + CameraSelector 2.5k + 构建/测试） |
| 处于重复/平行/投机结构中的代码 | 约 30–40%（~15,000 行） |
| 直接可删除（零功能损失） | ~3,500–4,500 行（死代码 + 仪式性抽象） |
| 合并后可再削减 | ~8,000–10,000 行（MD3 去三份化、着色器去内联、SIMD 坍缩等） |
| **当前已损坏的流程** | **2 项：Release 流水线（补丁路径失效）；测试体系（34 个测试在 Release 下全部空转）** |
| 潜在内存安全隐患 | 1 项：同名异构 MD3.h 的 ODR/布局踩踏风险 |

**根因模式：迁移不闭环。** 全仓反复出现同一病灶——引入新机制后不退役旧机制：MD3 提取到 src/ui/md3 但两份旧拷贝仍在编译；新 AppStates.h 建成但旧 AppState.h 仍被 Windows 使用；命令层建成但两端都绕过它；着色器编译迁到 CMake 但 457 行 ps1 未删；补丁移到 patches/ 但 CI 仍指向 scripts/；服务层抽象只有 macOS 单实现。每次"半程重构"都把一份代码变成两份。

**排序上的关键约束：任何大型重构（MD3 合并、AppState 迁移、后端拆分）都必须在 P0-2（测试可信化）落地之后进行，当前测试网兜不住任何回归。**

## 二、P0 — Critical（4 项）

### P0-1. Release 流水线已损坏：补丁应用逻辑四处复制且全部指向已迁移的旧路径
- **类别**：流程/重复 ｜ **严重程度**：Critical ｜ **合并自 1 条**
- **位置**：`.github/workflows/release.yml:12,41,52,141,159,209,296`
- **影响**：补丁于 b4f138f（2026-07-16）迁至 patches/ 并改名，release.yml 仍在 4 个 job 执行 `git apply scripts/imgui_md3.patch` 等——文件不存在，git apply 以 128 退出，**build-tflite/build-base/build-opengl/build-diligent 全部失败，发布产物为零**；缓存 key 与 paths 过滤对不存在文件做 hashFiles，静默失效。且其中两处即使路径修对也是冗余（CMake configure 与 build_tflite.cmd 内部已各自应用补丁）。
- **量化**：4 个 job 阻断；发布能力中断已 10 天；修复约 0.5 人日。
- **建议**：删除 4 处手工 git apply；build-diligent/build-tflite 依赖脚本/CMake 内置补丁应用，build-base/build-opengl 改调统一入口 `scripts/apply_third_party_patch.cmd imgui-md3`；缓存 key 改用 patches/ 路径或子模块 SHA。**【速赢】**

### P0-2. 测试体系系统性失效：全绿结果不验证任何东西
- **类别**：测试/设计缺陷 ｜ **严重程度**：Critical ｜ **合并自 4 条**（NDEBUG 剥离断言 / terminate 吞退出码 / 基线测试传 nullptr / CI 不跑测试）
- **位置**：`tests/`（全部 21 个测试文件）；`src/platform/macos/CocoaHost.mm:195-197`；`tests/MetalObjectShaderBaselineTests.mm:98,120`；`.github/workflows/`
- **影响**：四重失效叠加——(a) 唯一断言机制是裸 `assert()`，当前 build/ 为 Release（-O3 -DNDEBUG），断言连同其副作用（`assert(device.Initialize())`）被整体编译移除，**34/34 测试空转通过**（实证：nm 无 assert 符号、缺参运行退出码 0）；(b) 14 个 smoke 测试失败路径调 `[NSApp terminate:nil]` 以 exit(0) 终止，`return 1` 是死代码（LastTest.log 已出现"打印失败信息却记为 Passed"）；(c) MetalObjectShaderBaselineTests 丢弃 CMake 传入的 metallib 路径、以 nullptr 初始化——**最近核心开发内容 object shader 从未被真实对比过**；(d) 两个 workflow 均不执行 ctest，纯逻辑测试也只能靠本地手跑。
- **量化**：21 个测试文件、34 个 ctest 条目有效验证量为 0；其中 14 个整启 App 的测试每轮耗时 1–2 分钟纯属浪费；修复约 2–3 人日。
- **建议**：测试目标统一加 `-UNDEBUG` 或引入不受 NDEBUG 影响的 REQUIRE 宏；副作用移出断言表达式；RequestExit 改 `[NSApp stop:nil]` 或失败时 `std::exit(1)`；基线测试改 `main(argc, argv)` 并断言 argc==2；增加"故意失败必须非零退出"的哨兵测试防复发；GitHub Actions 加 macOS runner 至少跑 unit 层。**此项是其余一切重构的前置条件。**

### P0-3. MD3 UI 库存在三份拷贝（11,845 行），并伴生同名异构头文件的内存踩踏隐患
- **类别**：重复/设计缺陷 ｜ **严重程度**：Critical ｜ **合并自 4 条**（两后端重复 / 三份拷贝实证 / CMake 仍编译旧副本 / ODR 隐患）
- **位置**：`src/ui/md3`（3,855 行，macOS 用）、`src/OpenGL/md3`（3,800 行，vcxproj:233-244 编译）、`src/Diligent/md3`（4,190 行，CMakeLists.txt:389-392 编译）；隐患在 `src/platform/macos/CMakeLists.txt:25`
- **影响**：commit ed588cb 的"提取独立模块"只完成一半。ui 与 OpenGL 版主体文件逐字节相同；Diligent 版已发散（MD3Context.cpp 1,362 vs 810 行）。每个控件修复/主题调整须做 2–3 遍且已在漂移。**更危险的是**：ParticleSaturnMacOSImGui 把 src/OpenGL/md3 导出到 include path，两个 MD3.h 中 `MD3Context` 布局不同（ui 版多一个 `bool useOpenGL` 字段）——目前仅靠 include 顺序侥幸正确，链接顺序一变即静默内存踩踏，无任何编译/链接诊断。
- **量化**：三份合计 11,845 行，冗余约 8,000 行；维护成本 ×3；修复约 1–2 人周（含 Windows 特有增量的平台化）。
- **建议**：第一步（当天可做）：从 macOS target 移除 src/OpenGL/md3 的 include，消除 ODR 隐患；第二步：两个 Windows 目标改链 ParticleSaturnMD3（src/ui/md3 已含 _WIN32/glad 分支），将 Diligent 特有增量移入平台分支后删除两份旧拷贝。

### P0-4. DiligentBackend 上帝对象：6,221 行单文件承载全部渲染职责
- **类别**：架构 ｜ **严重程度**：Critical ｜ **合并自 5 条**（单体巨文件 / 17 个 Create*PSO 重复 / 347 次 backend 运行时分支 / 68+ 成员变量 / 平台特性耦合）
- **位置**：`src/Diligent/DiligentBackend.cpp`（6,221 行 / 262KB）、`DiligentBackend.h:126-365`
- **影响**：单类混合三后端初始化（D3D11/D3D12/Vulkan）、SwapChain/透明模式、DirectComposition（392 行）与 Vulkan-D3D12 互操作（950 行）等小众特性、17+ 渲染特性的 PSO 创建、资源管理、帧渲染、ImGui、手部追踪。内部三大结构病：(1) 17 个 Create*PSO 方法 90% 结构相同（~1,200 行样板，CreateShaderFromBytecode 模式重复 76 次），改任何 PSO 设置须动 17+ 处；(2) backend_ 在 Init 后不变却被运行时检查 347 次（21 处 Vulkan 分支），编译期常量按运行时变量处理；(3) 68+ 个 RefCntAutoPtr 成员摊平在一个命名空间，资源生命周期不可推断。新增一个渲染特性 = 修改 6,000 行文件。

- **建议**：分阶段拆分——PipelineBuilder 统一 PSO 创建（17 个方法 → ~200 行 + 描述符表）；资源按特性聚合成 struct/组合类（BloomResources、ParticleResources）；DirectComposition/VulkanD3D12Interop 移为可选模块（ifdef）；后端差异用编译期选择或拆分子类消除 347 处运行时分支。

## 三、P1 — High（11 项）

### P1-8. Metal 后处理每帧重载 metallib 并重建 compute PSO 【速赢】
- **类别**：性能 ｜ **合并自 1 条**

### P1-9. 仪式性 RenderGraph：拓扑排序可证明恒为插入序，三后端每帧重建 + 空转 TexturePool
- **类别**：过度工程 ｜ **合并自 3 条**（单点使用 / 每帧重建恒等排列实证 / TexturePool 零池化）
- **位置**：`src/render/RenderGraph.cpp`（159 行）+ `ResourceRegistry.cpp`；每帧重建于 DiligentVulkanAdapter.cpp:543、MetalBackend.mm:869、OpenGLFrameRenderer.mm:26
- **量化影响**：三个 macOS 后端每帧执行 7–11 次 AddResource + 10–25 次 AddPass（std::string/std::function 各一份）+ O(V·E) 拓扑排序，~30–45 次堆分配/帧，而 lastWriter 按插入序赋值使排序结果必为 0..N-1 恒等排列——图交付的唯一真实功能是"pass 返回 false 时提前退出"；还发明 1×1 伪纹理喂图边。TexturePool 从不创建/持有/复用任何 GPU 资源，纯代际索引分配器。

## 第二部分：全部原始发现（按严重程度分组）

### 🔴 Critical（4 项）

#### 🔴 -1. Monolithic 6221-line DiligentBackend violates single responsibility

- **类别**: 过度设计
- **位置**: `src/Diligent/DiligentBackend.cpp`
- **描述**: DiligentBackend.cpp is a 6221-line (262KB) monolith containing 39 methods that handle: multi-backend initialization (D3D11/D3D12/Vulkan), SwapChain management, transparent mode switching, native D3D11 blit optimizations, DirectComposition interop, Vulkan-D3D12 interop, PSO creation for 17+ rendering features (particles, stars, bloom, acrylic, tone mapping, seven-segment FPS), resource management, frame rendering, ImGui integration, and hand tracking. The class has 68+ RefCntAutoPtr member variables for textures/buffers/pipelines. Each Create*PSO method repeats 20-40 lines of boilerplate shader loading with if (backend_ == Vulkan) branches (21 occurrences, 347 backend-specific mentions total).
- **影响**: Impossible to test, modify, or understand in isolation. Adding a new rendering feature requires touching a 6000+ line file. Backend-specific bugs cascade across all features. Code duplication in every PSO creation method. Violates Open/Closed Principle - every new feature modifies this god object.
- **建议**: Split into focused components: RenderPipelineFactory (PSO creation), SwapChainManager (transparent mode switching), FeatureRenderers (Bloom, Acrylic, Particles as separate classes), BackendAdapter (D3D11/D3D12/Vulkan initialization). Extract common PSO creation patterns into template methods. Target: no file over 800 lines, no class with >15 public methods.

#### 🔴 -2. MD3 UI component library duplicated across two rendering backends

- **类别**: 代码重复
- **位置**: `src/OpenGL/md3/ (3,800 LOC) vs src/Diligent/md3/ (4,190 LOC)`
- **描述**: Material Design 3 UI library is fully duplicated between OpenGL and Diligent backends. MD3Theme.cpp is 100% identical between the two (only comment differences). MD3Widgets.cpp shares identical logic for the first 100 lines. The only difference is rendering API calls (glUseProgram vs PSO), but all business logic, animation systems, and interaction handling are duplicated.
- **影响**: 8,000+ lines of duplicated code requiring double maintenance effort. Any UI behavior change, animation tweak, or interaction logic update must be synchronized across two implementations. Synchronization drift already observed: Diligent MD3Context.cpp creates Ripple PSO using Diligent API (454 lines), OpenGL version uses glCreateProgram (758 lines), but core logic should be identical yet implemented separately.
- **建议**: Extract MD3 UI components into a backend-agnostic layer. Create src/ui/md3/ with unified business logic, animation, and interaction handling. Define rendering abstraction interface (DrawRoundedRect, DrawCircle, UploadTexture) with thin adapter layers for OpenGL and Diligent. Estimated savings: 6,000+ lines of duplicate code.

#### 🔴 -3. Release CI 中补丁应用逻辑四处复制，且全部指向已迁移的旧路径，发布流水线已损坏
